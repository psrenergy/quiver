  <action>
Create `tests/fixtures/` and copy both source CSVs into it under the ASCII names D-24 settled on:
the Energia file becomes `ma_energia_residencial.csv`, the GD file becomes `ma_gd_data.csv`. The
source filenames carry a non-ASCII character and spaces; the content is what the tests are about,
and a non-ASCII path is a cross-platform liability in git, CMake and CI for a property no
requirement asks for.

**Copy in binary. The bytes are the test.** The Energia file's leading UTF-8 BOM is PARSE-05's
subject and its CRLF endings are PARSE-06's; a copy that normalizes either silently deletes the two
requirements the real files were chosen to prove. Do not open either file in an editor, and do not
route the copy through a unix text tool. The GD file has no BOM and LF-only endings — that asymmetry
is itself useful and must also survive.

Verify after copying, and again after committing:
  - the Energia fixture's first three bytes are the UTF-8 BOM and its first line ends with a
    carriage return followed by a newline;
  - the GD fixture contains no carriage-return bytes at all;
  - both files' byte counts match their sources exactly.
Use a hex dump for the first check rather than a visual one — a BOM is invisible in a terminal.

**A `.gitattributes` exemption is REQUIRED before either file is staged, and this is the single
easiest way to silently void this plan.** D-24 assumed no normalization rule reaches `.csv` because
the per-extension lines only name `.cpp/.h/.dart/.jl/.py`. That assumption is wrong: the file's
FIRST line applies a text-auto rule to every path, and this machine's git is additionally configured
to convert line endings on checkout. Staging the Energia fixture as-is therefore rewrites its
carriage-return/newline pairs to bare newlines in the index — the working-tree copy still looks
correct on Windows, the tests still pass locally, and PARSE-06's real-file evidence is gone,
permanently and invisibly, including for every CI run on Linux. This was observed directly while
planning: git emitted a line-ending conversion warning for ordinary planning documents in this same
repository.

So: add a rule to `.gitattributes` exempting the fixture directory's CSV files from all line-ending
conversion — the marker that disables text handling entirely, scoped to `tests/fixtures/*.csv` so it
does not change how any other file in the repository is stored. Add it and stage it BEFORE staging
either fixture; an attribute added afterwards does not retroactively fix an already-normalized index
entry, and recovering from that needs an explicit re-add. Put a one-line comment above the rule
saying these files' exact bytes are the test, so nobody tidies it away later.

Then confirm with `git check-attr -a` on the Energia fixture that text conversion is off, and re-run
the hex dump against the committed blob (`git show :&lt;path&gt;`) rather than only the working-tree file
— the working-tree file is exactly the copy that would still look right if this went wrong.

No CMake change is needed. `tests/schemas/` is the precedent: its files are never listed in CMake
and are located at run time from the compiled-in `__FILE__` of the test source, which is
working-directory independent. `tests/fixtures/` works the same way.

Record the fixture directory in the summary so plan 02-04's `tests/CLAUDE.md` update can describe
it.
  </action>

  <done>

    - Assert the header came from the file's SECOND line (the column names), not its first (the

  <action>
Add a test reading the committed Energia fixture end-to-end through a Lua script.

Copy the fixture into the sandbox first, with `std::filesystem::copy_file` from
`quiver::test::path_from(__FILE__, "fixtures/ma_energia_residencial.csv")` to `sandbox / "..."`.
The copy is mandatory, not incidental: `db:read_csv` resolves a relative path against the database
directory, and that sandbox is not the source tree. `copy_file` moves bytes as-is on both Windows
and POSIX, so the BOM and the CRLF endings reach the reader intact.

The file's real shape is one junk row ABOVE the header and one units row BELOW it — not the two
junk rows above the header that the ROADMAP's third success criterion describes. Satisfy the
criterion's intent by covering the real shape: read with `{ header_row = 2 }` so the block-title
line is consumed as preamble and the units row arrives as the first data row, then have the script
start its loop at the second row. That skip is one line of script offset, which is exactly why D-22
rejected a `skip_rows` option — every documented option costs prompt tokens forever and no
requirement asks for this one.

The script does the transformations, and the test asserts the transformed values (D-23). Two
transformations, both on columns the research pinned by index against the raw bytes: the date column
holds day-first slash-separated dates, reformatted to year-then-month; the value column holds
numbers padded with surrounding spaces and using apostrophes as thousands separators, stripped to a
plain number.

**The number conversion must use the extra parentheses.** Lua's `gsub` returns two values, so
passing its result straight into `tonumber` hands the replacement count over as `tonumber`'s base
argument and silently yields nil, which would then compare unequal without ever pointing at the
cause. Wrapping the `gsub` call in its own parentheses truncates it to one value. This is D-23's
documented trap, and having it exercised by a passing test here is what lets Phase 3 write it up as
a demonstrated hazard rather than a claim.

Ignore the annual block in columns one through three: it stops being populated partway through the
file, so only the monthly block's columns carry the whole range. Do not assert on the annual
columns.
  </action>

file — so the conversion is a direct one. Keep it that way rather than reusing the Energia script's
