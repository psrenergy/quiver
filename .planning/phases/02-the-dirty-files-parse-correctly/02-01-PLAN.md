Thread a `header_row` option from the Lua options table through to `csv::CSVFormat`, per D-20:
1-based at the Lua boundary, `0` meaning "this file has no header", default `1`.

**`src/csv_read.h`** — add `int64_t header_row = 1;` to `Options`, with a one-line comment stating
it is 1-based and that 0 means no header (D-20). Keep `int64_t` — house counts are `int64_t`, not
`size_t` or `int`.

**`src/csv_read.cpp`, `make_format()`** — replace the single `format.header_row(0)` call with a
branch on `options.header_row`: zero calls `format.no_header()`, anything else calls
`format.header_row(...)` with the value minus one (csv-parser is 0-based). Clamp the subtracted
value into `int` range before the cast — a caller-supplied value above `INT_MAX` would otherwise
truncate into a *negative* int and trip the very side effect the next paragraph is about; any such
row index is past the end of every real file anyway, so it lands on Task 2's error.

**The ordering is the point of this task and it is not cosmetic.** `CSVFormat::header_row(int row)`
assigns `variable_column_policy = KEEP` whenever `row < 0`
(`build/_deps/csv_parser-src/include/internal/csv_format.cpp:44`), and `no_header()` is defined as
`header_row(-1)`. Today `make_format` calls `variable_columns(...)` first and `header_row(0)` second,
which is safe only because `0` is not negative. Adding the no-header branch in that same textual
position silently downgrades the `KEEP_NON_EMPTY` pin to `KEEP` for every no-header read, which
resurrects the phantom-blank-line rows Phase 1's D-13 exists to prevent. So: set the header mode
FIRST and call `format.variable_columns(csv::VariableColumnPolicy::KEEP_NON_EMPTY)` LAST, and extend
the existing D-12 comment block (do not replace it) with a sentence naming the side effect and
citing `csv_format.cpp:44`, so a future minimal-diff edit does not reorder it back. Task 3 adds the
test that fails if it is reordered.

**`src/lua_runner.cpp`, `read_csv_options_from_lua`** — this is the one shared decoder both entry
points route through (LUA-03); adding the option here is what stops `db:read_csv` and
`db:read_csv_stream` from diverging. Widen the unknown-key rejection so `"header_row"` is accepted
alongside `"separator"`, collect its value the same way `separator_value` is collected, and validate
it after the traversal (throwing out of sol2's `for_each` abandons the traversal mid-stack — Phase 1
D-17). Two checks, both raising a Pattern 1 message naming the option:
  - the value's `get_type()` must be `sol::type::number` — checking the Lua type explicitly rather
    than routing through `lua_cell_as`, which surfaces a raw sol2 stack message that is neither
    Pattern 1 nor stable across build types (Phase 1 D-17). This also rules out a quoted `"2"`,
    which Lua's own string→number coercion would otherwise let through.
  - `.is&lt;int64_t&gt;()` must hold, which rejects a fractional number such as `2.5`. This is the
    house idiom already used for group-column indices in the same file. `SOL_SAFE_NUMERICS=1` is set
    unconditionally in `src/CMakeLists.txt` (not gated on build type), so the precision check holds
    in Release as well — this was an open question in the research and is now settled; do not spend
    a probe on it.
  Both failures raise `option 'header_row' must be an integer`. A value below zero raises
  `option 'header_row' must not be negative` — a separate message, because "-1" is an integer and
  telling the user otherwise would be a lie. Both messages carry the `Cannot &lt;operation&gt;: ` prefix
  from the `operation` parameter, so the stream entry point names itself (Phase 1 D-19).

**The `db:read_csv` binding itself needs no change.** Its `if (!header.empty())` guard already omits
`header` from the returned table when there is none — its own comment calls that guard
"forward-looking", and this is the case it was looking forward to (D-01, D-20).

**`bindings/js/src/lua-api.ts`** — the CSV section currently states that `separator` is the options

break the stale-name or stdlib-list assertions.

Add the two tests described in `&lt;behavior&gt;` to `tests/test_lua_runner_read_csv.cpp`, in the

csv-parser does not signal a header row past the end of the file. `trim_header`
(`build/_deps/csv_parser-src/include/internal/csv_reader.cpp:74-83`) pops one raw record per
iteration up to the requested index and stops early when the queue empties, leaving `col_names`
unset and — because the trim loop already consumed every record — zero data rows, with no exception
raised anywhere. Verified empirically during research against the vendored 5.3.0 in this repo's
build tree: `header_row(5)` on a 3-line file constructed successfully with an empty header and zero
rows. So `Reader` must synthesize LUA-08's error itself.

In `Reader`'s constructor, after the `csv::CSVReader` has been constructed and its column names
retrieved, throw when the caller explicitly asked for a header (`options.header_row != 0`) and the
retrieved names came back empty. Message: `Cannot &lt;operation&gt;: header row &lt;N&gt; not found in file
'&lt;original_path&gt;'`, where `N` is the caller's own 1-based value and the path is the caller's own
spelling — both matching how the nine existing messages in this constructor already read (Phase 1
D-21, D-22). This is the tenth entry in that catalogue; add it to the comment listing the
evaluation order if one is present.

**Gate the check on the request, never on the header alone.** `header_row = 0` also yields an empty
header — by design, that is exactly how the binding knows to omit `csv.header` — so a check that
looked only at emptiness would either throw on every legitimate no-header file or succeed silently
on every past-EOF request. `options.header_row != 0` is the only available disambiguator and it is
available because the value is still in its pre-translation, Lua-facing form at this point.

**The throw must not be swallowed by the surrounding wrapper.** The existing `try` around the
`CSVReader` construction catches `std::exception` and re-prefixes it with
`Cannot &lt;op&gt;: cannot read file '...': `, which would double-prefix this message into nonsense.
Scope the `try` to the `CSVReader` construction itself and perform the empty-header check outside
it, mirroring how the three not-found/directory/empty checks already sit outside any try block in
this same constructor.

Also treat one behavioural note as deliberate rather than accidental: a file consisting of a single
blank line is non-empty (so it passes the existing size check) but may resolve to a zero-length
header, which this check now turns into a throw where Phase 1 returned an empty result. No existing
test covers that input and no requirement asks for it; if the executor observes it while writing
Test 1, record it in the plan summary rather than adding a guard for it.

Add the three tests in `&lt;behavior&gt;`, using `expect_lua_error` with the full expected message for
Tests 1-2 and a plain `lua.run` with Lua-side asserts for Test 3.
  </action>

no-header read, because `header_row` did not exist until Task 1.
