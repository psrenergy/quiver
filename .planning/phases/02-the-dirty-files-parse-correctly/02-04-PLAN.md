Close the phase: prove the new Lua option decoding behaves identically with sol2's safety getters
off, and write the paperwork the house rules require.

hidden Lua marshalling bugs in this repo. The `header_row` decoder is exactly the kind of

<task type="auto">
  <name>Task 1: Run the suite in a Release build, where sol2's safety getters are off</name>
  <files>(no repository files — a build and a test run)</files>
  <precondition>Every plan in waves 1 through 3 is committed; a Release run before the tests exist would verify nothing.</precondition>
  <read_first>
    - `.planning/phases/02-the-dirty-files-parse-correctly/02-RESEARCH.md` — Finding 7, which
      records why the `release` preset is the wrong lever and gives the runnable commands.
  </read_first>
  <action>
Configure and build a Release tree with tests enabled, then run the Lua suite against it.

**Do not use the `release` CMake preset.** It sets the test-building option to OFF, so it produces a
Release tree with no test binary at all — a run against it would report success while testing
nothing, which is the exact failure mode this requirement exists to catch. Configure explicitly with
tests and the C API on, into a separate directory so the day-to-day Debug tree is not reconfigured
out from under subsequent work. `scripts/build-all.bat --release` is the house-blessed alternative
and does set the option correctly, at the cost of reconfiguring the shared build directory in place
and running every binding suite as well.

Run the whole `LuaRunner` family, not just the CSV suite — the concern is sol2 marshalling in
general, and the filter that covers every Lua-facing test costs nothing extra.

What is actually being checked: sol2 turns its safe getters off whenever the build defines NDEBUG,
which a Release configuration does on its own — this repo sets no overriding define. The precision
check behind the fractional-`header_row` rejection is governed by a numerics setting that
`src/CMakeLists.txt` sets unconditionally rather than per build type, so it is expected to hold; the
run is what turns that expectation into evidence. Research left this as an open assumption and it
has since been settled by reading the CMake file — do not spend a probe re-investigating it, just
run the suite.

Record in the summary: the exact configure and build commands used, the build type, the test filter,
and the pass/fail counts. If any test passes in Debug and fails in Release, that is a real defect in
the new decoder and not a test-environment problem — stop and report it rather than relaxing the
test.
  </action>
  <verify>
    <automated>cmake -S . -B build-release -G Ninja -DCMAKE_BUILD_TYPE=Release -DQUIVER_BUILD_TESTS=ON -DQUIVER_BUILD_C_API=ON &amp;&amp; cmake --build build-release --config Release &amp;&amp; ./build-release/bin/quiver_tests.exe --gtest_filter='LuaRunner*'</automated>
  </verify>
  <done>
A Release build with tests enabled exists, and every `LuaRunner*` test passes against it with the
same results as the Debug run.
  </done>

  <action>
Update the documentation nearest each change (DOC-04).

**`src/CLAUDE.md`** — the existing paragraph lists the settings pinned in `make_format` and why each
library default is wrong. Extend it: the header row is now caller-selectable rather than hardcoded,
and the order of the calls in that function is load-bearing because setting a negative header row
resets the variable-column policy as a side effect, so the policy pin has to come last. State the
consequence — reverting the order reintroduces phantom blank-line rows for no-header reads — so the
next person to make a minimal-diff edit there has the reason in front of them. Also record the
past-EOF error the reader now synthesizes, since csv-parser reports that condition as a successful
read of nothing.

**`tests/CLAUDE.md`** — its entry for the CSV read suite says the suite's fixtures are written at
run time into the sandbox rather than committed. That is now only half true: the two real Maranhão
files live under the new `tests/fixtures/` directory and are copied into the sandbox by the tests
that use them. Describe the directory, say why those two are committed (their exact bytes — a
leading BOM and CRLF endings in one, neither in the other — are what two of the parser requirements
assert, so they cannot be regenerated), and note that like `tests/schemas/` they need no CMake
registration because they are located from the compiled-in source path.

**`CHANGELOG.md`** — add an entry under the existing unreleased version, in the Added section
alongside Phase 1's CSV entry. Describe the option from a caller's point of view: which row is the
header, that it counts from one, that zero declares the file has no header and leaves the header
absent from the result, and that a row past the end of the file raises rather than returning
nothing. This is additive with a default matching the previous behavior, so it is not breaking and
needs no version bump beyond whatever the unreleased heading already carries.

Do not restate the option's documentation in a fourth place — `bindings/js/src/lua-api.ts` already
carries the caller-facing description from plan 02-01, and that text is interpolated into every
agent session, so duplicating it costs tokens without adding reach.
  </action>
  <verify>
    <automated>grep -q 'header_row' src/CLAUDE.md &amp;&amp; grep -q 'fixtures' tests/CLAUDE.md &amp;&amp; grep -q 'header_row' CHANGELOG.md</automated>
  </verify>
  <done>
`src/CLAUDE.md` explains the header-mode ordering constraint and the synthesized past-EOF error;
`tests/CLAUDE.md` describes `tests/fixtures/` and why those two files are committed;
`CHANGELOG.md` carries the `header_row` entry under the unreleased version.
  </done>
