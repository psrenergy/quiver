call throws with that entry's full message substring. Use `expect_lua_error` throughout and pin the
whole `Cannot <op>: ...` prefix plus the distinguishing text, never a lone keyword — an escape test
that only checks "it threw" goes green when the call fails for an unrelated reason and certifies
containment it never exercised.

The five TEST-03 sandbox negatives, each written for **both** `db:read_csv` and
`db:read_csv_stream` so the assertion covers the entry point's own operation name:
1. A relative path climbing out of the database directory, and separately an absolute path outside
   it, both expecting `Cannot <op>: path '<the script's own spelling>' escapes the database
   directory '<root>'`. Pin the script's spelling of the path in the message, not the resolved
   absolute one.
2. A database opened at `:memory:`, expecting
   `Cannot <op>: database is in-memory, file operations are unavailable`. Build this case with a
   separate in-memory `Database` and its own `LuaRunner`; it cannot share the sandbox fixture's
   file-backed database.
3. A path naming a file that does not exist, expecting `Cannot <op>: file not found: <p>`. This is
   the case the sandbox helper does not catch on its own — it resolves with `weakly_canonical`,
   which tolerates a missing path — so a green here is the evidence the separate existence check is
   actually present.
4. A directory given where a file was expected, expecting `Cannot <op>: path is a directory: <p>`.
   Create the directory inside the sandbox first.
5. The positive control: a CSV inside a subdirectory of the database directory, read successfully
   through both entry points with the right rows. Without this one the other four would all pass
   against an implementation that rejects every path.

Then the remaining catalogue entries, for whichever entry point exercises them most directly, plus
a stream-form variant wherever the operation name is the thing under test:
- The empty-file throw, already present from plan 01-01 — extend it to `db:read_csv_stream` so both
  forms agree on an empty file rather than one throwing and the other reporting zero rows.
- The parser wrapper: drive a failure that reaches `csv::CSVReader` and assert the message begins
  `Cannot <op>: cannot read file '` — for instance a path made unreadable, or whatever the platform
  makes reliably reproducible in the sandbox. If no such case is reliably reproducible on this
  platform, assert instead that the wrapper exists by pinning it as a source-level check and record
  in the SUMMARY that the runtime path was not exercisable — do not delete the requirement silently.
- Ordering: a call that trips two conditions at once must report the earlier one. Assert that an
  in-memory database with a bad options table reports the in-memory error, and that an escaping path
  to a file that also does not exist reports the escape error rather than file-not-found.
- Adjacency: an options table carrying both an unknown key and a non-string `separator` reports the
  unknown-key error.
- The blanket rule: a small helper or a loop over the negative cases asserting every message from
  this suite starts with `Cannot read_csv: ` or `Cannot read_csv_stream: `, so a future change that
  lets a raw csv-parser, `std::filesystem` or sol2 message through fails here rather than silently
  reaching a script.

Finally, assert that after each sandbox negative the CSV file (where one exists) can still be
deleted — no failure path leaves a reader open.
