Author eight directories under `tests/schemas/ui/`, each with a `schema.sql` (Configuration table
plus the collection tables its TOML describes, satisfying `SchemaValidator`) and a `ui/`
subdirectory. Every file is a hand-written miniature, LF line endings, UTF-8 without BOM. Each
directory pins exactly one rule unless a real model file genuinely carries several.

`bess_like/` — CORPUS-01 (BESSOperation), PARSE-03, PARSE-07, PARSE-08. Collection `Storage`.
`ui/main.toml` lists `["storage"]`. `ui/enum.toml` declares a `look_ahead` vocabulary with **all
bare-string** labels and **gapped, non-zero-based, negative and large** codes — use ids `-1`, `0`,
`3`, `7` and `9223372036854775807` so both the gap tolerance and the int64 range are data-pinned.
`ui/storage.toml` sets `id = "Storage"` and interleaves, in this order: `[[attribute_group]]` with
`id = "degradation"` and `label = "Degradation Curve"`, then `[[attribute]]` with
`id = "degradation"` and `label = "Degradation Rate"`, then `[[attribute_group]]` with `id = "rte"`
and `label = "Round Trip Efficiency Curve"`, then two more `[[attribute]]` blocks —
`id = "capacity"`, `label = "Installed Capacity"` and `id = "cycles"`,
`label = "Rated Cycle Count"`. Every label in this directory is a bare string.

**The two `degradation` labels MUST differ** (`Degradation Curve` on the group block,
`Degradation Rate` on the attribute block). Phase 1 renders no group UI metadata at all — only
scalar lines — so the *only* observable symptom of a one-map implementation (the group block
overwriting the attribute block) is the `degradation` **scalar** line showing the group's label. If
both blocks carried the same label, `AttributeAndGroupIdsAreSeparateNamespaces` in plan 01-04 would
pass whether or not the namespaces are actually separate. Same reasoning gives the two trailing
`[[attribute]]` blocks distinct labels, so PARSE-08's "still parsed after a group block" is
assertable.

**The schema must make the collision real, not notional:** `schema.sql` creates `Storage` with a
scalar column named `degradation` **and** a vector group table `Storage_vector_degradation`, plus a
`Storage_vector_rte` for the second group. Without both, `degradation` is an id collision only in
the TOML and PARSE-07 cannot be observed through `describe_collection`.
**Neither group table's value column may be named after its group.**
`src/schema_validator.cpp:284-288` throws
`"Duplicate attribute 'degradation' found in table 'Storage_vector_degradation' (already defined in
collection 'Storage')"` for any group value column matching a scalar column of the parent
collection — so `Storage_vector_degradation(id, vector_index, degradation REAL)`, the obvious
spelling, makes `from_schema` fail for the entire fixture. Name the value columns `rate` and
`efficiency` respectively (`Storage_vector_degradation(id, vector_index, rate REAL)` and
`Storage_vector_rte(id, vector_index, efficiency REAL)`), and check the same rule against every
other fixture's group tables before committing.

`foresight_like/` — CORPUS-01 (Foresight), PARSE-04, and the corpus's **encoding** fixture.
Collection `EconomicDriver`.

`schema.sql` creates `EconomicDriver (id INTEGER PRIMARY KEY AUTOINCREMENT, label TEXT UNIQUE NOT
NULL, forecast_model INTEGER, notes TEXT) STRICT;` beside the required `Configuration` table. The
`forecast_model` INTEGER column is load-bearing: **without an attribute bound to the `model`
vocabulary, nothing in any report ever renders it**, and every downstream assertion that quotes a
`model` label has nothing to assert. (In the real Foresight repo `model` is bound in
`consumption.toml`, not `economic_driver.toml` — the vocabulary and the collection come from
different files there. This fixture binds them in one, deliberately.)

`ui/enum.toml` declares a `model` vocabulary with exactly four entries, in **this declaration
order** — which is deliberately *not* code order, because declaration-order-not-sorted-by-code is
otherwise unobservable anywhere in the corpus (`bess_like`'s codes happen to be ascending):

1. `id = 2` — `label.en = "Local Linear Trend"`, `label.es = "Tendencia Lineal Local"`,
   `label.pt = "Tendência Linear Local"` (dotted, exact-locale leg → `Local Linear Trend`)
2. `id = 3` — bare `label = "ARIMA"`, sitting between dotted entries (bare-wins leg → `ARIMA`)
3. `id = 5` — `label.en = "Seasonal Naïve"`, `label.es = "Ingenuo Estacional"`,
   `label.pt = "Ingênuo Sazonal"` (exact-locale leg → `Seasonal Naïve`, **non-ASCII at locale
   `en`** — this is the corpus's primary encoding literal)
4. `id = 4` — **only** `label.es = "Regresión Lineal"` and `label.pt = "Regressão Linear"`, no `en`
   (first-key-in-map-order leg, `"es" < "pt"` → `Regresión Lineal`, **also non-ASCII**)

Entries 3 and 4 are both accented on purpose: entry 3 proves UTF-8 survives on the plain
exact-locale path, entry 4 proves it survives on the fallback path, so an encoding failure and a
fallback failure cannot be confused for one another. An accented `pt`-only value would be selected
at no Phase-1 locale and would prove nothing — `Residencial`, the real repo's `es` value for that
entry, is pure ASCII, which is exactly the trap this spelling avoids.

`ui/main.toml` lists `["economic_driver"]`. `ui/economic_driver.toml` carries `id = "EconomicDriver"`,
a collection-level `label = "Economic Drivers"`, an `[[attribute]] id = "forecast_model"` with
`type = "enum"`, `enum = "model"` and `label = "Forecast Model"` — the binding that makes the whole
vocabulary render — plus one attribute (`id = "notes"`) whose `tooltip` is an empty table `{}` and
whose `label` is the empty string.

`htd_like/` — CORPUS-01 (HydroThermalDispatch), PARSE-10, and the **missing-`id`** case.

`ui/hydro_plant.toml` carries `id = "HydroPlant"` — the snake_case filename to PascalCase table
name mapping — with a plain `[[attribute]] id = "date_time"` block carrying

`ui/thermal_plant.toml` is a **well-formed TOML file that declares no `id` key at all** (a

`ui/enum.toml` declares `bool` as `{0: "Disable", 1: "Enable"}` (the real repo's spelling, which

reading the wrong fixture). `schema.sql` creates a `HydroPlant` table with a
`HydroPlant_time_series_generation` group whose dimension column is `date_time`, **and** a
`ThermalPlant` table so the skipped file is skipped for its missing `id` and not for a missing
table.
