**Unknown keys (PARSE-05, D-26).** While parsing one collection file, accumulate the names of
every key the parser does not consume — at main, collection and attribute level — into a local
`std::vector<std::string>`, and emit exactly **one** `logger->debug(...)` line per file naming the
file and the joined key list. Do not log per key: the real corpus has 736 attributes and one real
occurrence. An unknown key never throws, never skips the file, and never prevents the config from
publishing. The consumed attribute keys stay exactly `id`, `label`, `tooltip`, `unit`, `hide`,
`enum` and `format`; Hub's `tab`, `type`, `read_only` and `enabled_if` are among the ignored set,
so the fixture proves both the "newer Hub" case and the "Hub key Quiver does not want" case.
Sort the accumulated names before joining so the log line is deterministic.

**`format` table form (PARSE-06, D-14).** Accept both shapes. A `toml` string value is stored
verbatim in `UIMetadata::format`. A `toml` table value is read by trying `data`, then
`element_view`, then `collection_view`, then `edit`, and storing the **first present** value
verbatim; when none is present the field stays empty. Record this precedence in a comment on the
field in `src/ui_config.h` and note that it exists because Phase 1's record carries one string —
whether META-01 needs all four keys is Phase 3's call. Quiver classifies neither format grammar and
must never inspect the string's content. A value of any other TOML type (an array, an integer) is
ignored like an unknown key rather than thrown on.

**Absent or zero-byte `enum.toml` (PARSE-09).** `from_directory` checks
`std::filesystem::exists` before reading `enum.toml`; when absent, `vocabularies` stays empty and
the walk continues. When present but empty, the content path must survive a zero-length string —
RESEARCH assumption A2 says toml++ parses an empty document to an empty table; if it does not, wrap
that one call so an empty file is treated as an empty table rather than letting it fail the whole
config. Never look for a `themes/` directory: it is out of scope for this milestone and its absence
must not be a condition the parser checks.

**PascalCase id mapping (PARSE-10).** `main.collections` lists snake_case **filenames**; each
file's own `id` field carries the PascalCase **SQL table name**. `UIConfigSet::collections` is
keyed by the `id`, never by the filename, so a renderer looking up a collection by its SQL table
name finds it. A file whose `id` is missing or empty is ignored with a debug log rather than
throwing — the config as a whole still publishes, because an unusable entry is not a malformed
document. Never derive one spelling from the other: no snake-to-Pascal transformation exists in
this codebase and `src/CLAUDE.md` forbids hand-rolled name splitting.

**Dual id namespace and interleaving (PARSE-07, PARSE-08).** Confirm by reading the code written
in plan 01-01 that `[[attribute]]` entries land in `UICollectionConfig::attributes` and
`[[attribute_group]]` entries in `::groups`, that neither map is consulted when writing the other,
and that a single forward pass over the file handles blocks in whatever order they appear. If the
tracer's implementation folded the two into one map or assumed a block order, fix it here — this is
the plan that owns those two requirements.

**Orphan collection files (PARSE-01, D-23).** The load set comes exclusively from
`main.collections`. Separately — and this is a different act, not a loophole — list the `ui/`
directory once, collect every `*.toml` whose stem is neither `main`, `enum`, nor a listed entry,
`std::sort` the result for platform stability, and store it in `UIConfigSet::unlisted_files`.
Nothing in Phase 1 reads that member; it exists because parse time is the only moment the directory
listing and the collections list are both in hand, and Phase 5's VALID-05 needs it. Add a comment
saying exactly that so the member does not read as dead code.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-13 | Denial of Service | unknown-key accumulation | medium | mitigate | Keys are accumulated per file into a local vector and emitted as one debug line, so a file with pathologically many unknown keys costs one log write, not one per key. The vector is function-local and dies with the file. |
| T-01-14 | Denial of Service | `format` table decoding | low | mitigate | Only four named keys are read from the table and only as strings; any other type is ignored like an unknown key, so no TOML value shape can force a throw out of the field reader. |
| T-01-15 | Tampering | unlisted-file recording | medium | mitigate | The directory listing feeds `unlisted_files` only; the load set still comes exclusively from `main.collections`. A file dropped into `ui/` is recorded, never executed as configuration — the property PARSE-01 exists to guarantee. |
| T-01-16 | Spoofing | PascalCase id keying | medium | mitigate | The config is keyed by the `id` the file declares, and a renderer looks up the SQL table name it already holds, so a file cannot decorate a collection it does not name. A missing or empty `id` is skipped with a debug log rather than defaulting to the filename. |
| T-01-17 | Denial of Service | zero-length `enum.toml` | low | mitigate | The empty-document path is explicitly exercised by the `empty_enum` fixture rather than assumed from the TOML grammar, so RESEARCH assumption A2 is closed by a test. |
| T-01-SC | Tampering | package installs | n/a | accept | No package manager runs in this plan. |
</threat_model>
