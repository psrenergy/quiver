<objective>
Give both entry points the one Phase-1 option — `separator`, defaulting to `,` — behind a decoder
strict enough that no bad option value can be silently swallowed.

Purpose: the likeliest user mistake is `db:read_csv("f.csv", ";")` — a separator passed positionally,
because every neighbouring db file-method in the shipped reference takes a bare scalar in slot 2. With
a permissive decoder that call parses the file with a comma, returns one wide column per row, and
fills the database with garbage without raising anything. This plan makes it throw.
Output: a shared options decoder in `src/lua_runner.cpp` wired into both bindings, the literal
options table in both `LUA_DB_API_REFERENCE` entries, and a rejection matrix in the test suite.
</objective>

  <action>
Add one shared options decoder as a file-scope static in `src/lua_runner.cpp` alongside the other
decoders — name it for what it decodes, e.g. `read_csv_options_from_lua` — taking the raw
`sol::object` and the operation name, and returning a `csv_read::Options`. Give both bindings a
trailing optional options parameter: `db:read_csv(path, opts)` and
`db:read_csv_stream(path, on_row, opts)`. Options tables are always last and always optional in this
codebase; keep that.

Declare the parameter as `sol::object`, **not** `sol::optional<sol::table>`, and hand-check its type
with an explicit `get_type()` comparison. This is the pattern `relation_target_from_lua` already
uses, and its comment already documents why. The reason is concrete and was verified by running the
real build: `src/CMakeLists.txt` defines `SOL_SAFE_FUNCTION`, but sol2 3.5.0 reads
`SOL_SAFE_FUNCTION_CALLS` / `SOL_SAFE_FUNCTION_OBJECTS` — a different macro entirely — so that
define is a no-op; the argument-check gate is off by default in Release; and sol2's optional checker
forwards to a non-raising path. The observable consequence on the existing surface is that
`db:export_csv("Configuration", "", "out.csv", "NOT_A_TABLE")` succeeds, writes the file and uses
defaults, silently. Fixing that globally changes behaviour on five existing call sites and is
deliberately out of scope here; this phase works around it locally by never using the leaky type.
Leave those five existing sites alone.

Decoder behaviour, in this order:
1. A missing parameter or an explicit `nil` yields default `Options` — this is the same as an empty
   table, and both are valid.
2. Anything that is not a Lua table throws `Cannot <op>: options must be a table`.
3. Walk the table's entries and **collect them first, then validate** — throwing out of sol2's
   `for_each` abandons the traversal mid-stack. Any key other than `separator` throws
   `Cannot <op>: unknown option '<key>'`, naming the offending key. This deliberately diverges from
   `parse_csv_options`, which ignores unknown keys: a typo'd key that silently does nothing is the
   exact failure mode this decoder exists to rule out, and it gets worse in Phase 2 when the header
   keys arrive and there is more to typo.
4. `separator` whose value is not a string throws `Cannot <op>: option 'separator' must be a string`.
   Check the Lua type explicitly rather than routing through the generic cell-conversion helper:
   that helper surfaces sol2's own message (`stack index -1, expected string, received number`),
   which is neither Pattern 1 nor stable across build types, and LUA-08 forbids a raw parser or
   stack message reaching the script.
5. A `separator` string whose length is not exactly 1 throws
   `Cannot <op>: option 'separator' must be a single character`. The zero-length and the
   multi-character cases both land here.

`<op>` is the operation name threaded in by the caller — `read_csv` from one binding and
`read_csv_stream` from the other — so the same bad table produces a message naming whichever entry
point the script actually called. Pass the resulting `Options` straight into the `csv_read::Reader`
constructor; the delimiter is still set in exactly one place, inside the reader.

Update both `LUA_DB_API_REFERENCE` entries in `bindings/js/src/lua-api.ts` to show the options table
as a **literal** — `{ separator = "," }` — in the signature rather than an abstract placeholder. The
placeholder is what invites the positional mis-call this decoder exists to reject. State that
`separator` is the only option and that an unknown key or a bad value throws. Keep it to those two
facts: this text is system-prompt payload interpolated into every agent session, so it pays for
itself only in traps that cause silent wrong answers.

Add to `tests/test_lua_runner_read_csv.cpp` the happy-path coverage for this task: a semicolon-
separated file read correctly through `db:read_csv(path, { separator = ";" })`; the same file read
through `db:read_csv_stream(path, fn, { separator = ";" })` yielding the same rows; a comma file
read with no options table and with an empty options table `{}` yielding identical results; and a
tab-separated file proving the option is not comma-or-semicolon special-cased.

Add the option-rejection matrix to `LuaRunner_ReadCsv`. Every case asserts the call **throws** —
a silent fallback to a default is the failure mode being ruled out, so a test that merely checks the
result is wrong would pass on the broken implementation this matrix exists to catch. Use
`expect_lua_error` and pin the full message substring from D-22, not a loose keyword, so a message
reworded later is caught rather than absorbed.

Cover, for `db:read_csv`:
- A string in the options slot — `db:read_csv("f.csv", ";")`, the positional mis-call — expecting
  `Cannot read_csv: options must be a table`.
- A number and a boolean in the same slot, expecting the same message. These are three separate
  wrong types and the decoder must reject all three; a single string case would pass against a
  decoder that only special-cases strings.
- An unknown key — use `delim`, the plausible abbreviation — expecting
  `Cannot read_csv: unknown option 'delim'`, with the offending key present in the message.
- A key that Phase 2 will legitimately add (a header-row key) expecting the same unknown-option
  message today, so the Phase-2 change is a deliberate edit rather than a behaviour surprise.
- A table carrying both `separator` and an unknown key, expecting the unknown-key message — the
  presence of a valid key must not excuse an invalid sibling.
- `separator` as a number and `separator` as a boolean, expecting
  `Cannot read_csv: option 'separator' must be a string`.
- `separator` as the empty string and as a two-character string, both expecting
  `Cannot read_csv: option 'separator' must be a single character`.

Then cover the per-entry-point naming rule: take one bad options table — the unknown-key case is
enough — and assert that through `db:read_csv_stream` the message reads
`Cannot read_csv_stream: unknown option '...'`. Add the positional mis-call for the stream form too:
`db:read_csv_stream("f.csv", fn, ";")` expecting
`Cannot read_csv_stream: options must be a table`. This is the assertion that fails if a later
change threads a single shared literal through the decoder instead of the caller's own operation
name.

Finally, assert the two forms agree on a valid table: reading the same semicolon file with the same
options through both entry points yields identical rows, and neither leaves the file open —
`std::filesystem::remove` on it succeeds afterwards.
